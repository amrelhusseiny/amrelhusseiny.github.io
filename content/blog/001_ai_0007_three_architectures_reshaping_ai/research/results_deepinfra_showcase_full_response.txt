# Configuring a Mid‑Size Enterprise Network – A Technical Guide  
*Target audience: senior network engineers, architects, and IT managers*  

**Scope** – This document walks through a complete, vendor‑agnostic design for a 500‑person campus network. It covers VLAN segmentation, IP addressing, firewall placement and rule‑sets, VPN/remote‑access, observability, high‑availability (HA) mechanisms, and security‑hardening best practices. All recommendations assume a modern, layered architecture built on Ethernet switching, a stateful firewall platform, and a centralized management plane.

## 1. Introduction & Design Principles  

A mid‑size enterprise (≈500 users) typically spans a single campus with multiple buildings, a data center, and a small branch office. The network must satisfy three overarching goals:

| Goal | Why it matters | Typical KPI |
|------|----------------|-------------|
| **Performance** | Low latency, predictable bandwidth for voice, video, and data | < 5 ms intra‑site latency, 95 % of users ≥ 100 Mbps |
| **Security** | Protect corporate assets, limit lateral movement, meet compliance | Zero successful external breach, < 1 % of internal traffic flagged |
| **Resilience** | Business continuity during link or device failure | < 5 min mean‑time‑to‑recover (MTTR) for critical services |

The design follows a **defense‑in‑depth** model: physical segregation → VLAN segmentation → IP subnetting → firewall filtering → endpoint hardening. All layers are documented, version‑controlled, and automated where possible (e.g., using Ansible, Terraform, or vendor‑agnostic APIs).

## 2. VLAN Design & Segmentation  

### 2.1 Why VLAN Segmentation Matters  

| Aspect | Impact of Segmentation |
|--------|------------------------|
| **Broadcast containment** | Reduces broadcast storms; each VLAN is its own broadcast domain. |
| **Security isolation** | Limits ARP spoofing, DHCP attacks, and lateral movement. |
| **Policy enforcement** | Enables per‑VLAN QoS, ACLs, and monitoring. |
| **Simplified troubleshooting** | Fault domains are smaller and easier to isolate. |

### 2.2 Grouping Users & Devices  

| Business Function | Typical Devices | Recommended VLAN ID (example) |
|-------------------|----------------|--------------------------------|
| Corporate LAN – Office Users | Desktops, laptops, IP phones | **10** |
| Guest Wi‑Fi (public) | Guest laptops, smartphones | **20** |
| Voice (IP‑Phone) | IP phones, soft‑phone clients | **30** |
| Data Center Servers | Application, DB, storage servers | **40** |
| Management & Ops | NMS, syslog, backup appliances | **50** |
| Security Appliances (IDS/IPS, firewalls) | Inline sensors | **60** |
| Wireless Controllers | AP management | **70** |
| IoT / Building Automation | Sensors, HVAC, cameras | **80** |
| Remote Site / Branch | Edge router, WAN link | **90** |
| Development / Test | Lab servers, VMs | **100** |

> **Tip:** Keep VLAN IDs under 4094 (standard 802.1Q range) and allocate them in blocks (e.g., 10‑99 for production, 100‑199 for labs). Reserve a “future” block (e.g., 200‑299) for expansion.

### 2.3 Physical vs. Logical Mapping  

| Layer | Example Implementation |
|-------|------------------------|
| **Core Switches** | Trunk all VLANs (10‑100) to each other using 802.1Q. |
| **Distribution Switches** | Only trunk VLANs required for the attached access layer (e.g., a floor with VLAN 10, 30, 20). |
| **Access Switches** | Port‑based or MAC‑based VLAN assignment (static for servers, dynamic for BYOD via 802.1X). |
| **Wireless LAN Controllers (WLC)** | Map SSIDs to VLANs (Guest → 20, Corporate → 10, Voice → 30). |

### 2.4 Example VLAN Configuration Table  

| VLAN ID | Name | Purpose | Tagged/Untagged Ports (example) | MTU (bytes) |
|--------|------|---------|--------------------------------|------------|
| 10 | **CORP** | Corporate workstations & phones | Trunk on core/distribution, access ports untagged on floor‑1 switches | 1500 |
| 20 | **GUEST** | Guest Wi‑Fi (no internal resources) | Trunk on core, access ports untagged on guest APs | 1500 |
| 30 | **VOICE** | SIP phones, QoS‑priority traffic | Trunk on core, access ports untagged on voice‑floor switches | 1500 |
| 40 | **DC** | Data‑center servers (production) | Trunk on core, access ports tagged on server NICs (VLAN 40) | 9000 (jumbo) |
| 50 | **MGMT** | Management network (NMS, consoles) | Trunk on core, access ports tagged on management NICs | 1500 |
| 60 | **SEC** | Inline security appliances | Trunk on core, access ports tagged on IDS/IPS | 1500 |
| 70 | **WLC** | Wireless controller traffic | Trunk on core, access ports tagged on controller | 1500 |
| 80 | **IoT** | Building automation, cameras | Trunk on core, access ports tagged on IoT switches | 1500 |
| 90 | **BRANCH** | WAN edge to remote site | Trunk on core, access ports tagged on edge router | 1500 |
| 100 | **DEV** | Development & test labs | Trunk on core, access ports untagged on lab switches | 1500 |

## 3. IP Addressing & Subnetting  

A well‑structured IP plan mirrors the VLAN layout, simplifies routing, and eases firewall rule creation.

### 3.1 Choosing the Address Space  

* **Private IPv4** – 10.0.0.0/8 is the most flexible for a 500‑user campus.  
* **IPv6** – Optional but recommended for future‑proofing; use a /48 Unique Local Address (ULA) block (fd00:abcd:1234::/48).  

### 3.2 Subnet Sizing Rules  

| Subnet Size | Hosts usable | Typical use case |
|-------------|--------------|------------------|
| /24 (255.255.255.0) | 254 | Small VLANs (guest, voice) |
| /23 (255.255.254.0) | 510 | Medium VLANs (corporate, IoT) |
| /22 (255.255.252.0) | 1022 | Large VLANs (data‑center, management) |

**Rule of thumb:** Allocate the smallest subnet that comfortably fits the projected device count plus a 20 % growth buffer.

### 3.3 Complete Addressing Plan  

| VLAN ID | Subnet (IPv4) | CIDR | Netmask | Usable IP Range | Broadcast | Primary Gateway |
|--------|---------------|------|---------|----------------|-----------|-----------------|
| 10 | 10.10.10.0 | /24 | 255.255.255.0 | 10.10.10.1‑10.10.10.254 | 10.10.10.255 | 10.10.10.1 |
| 20 | 10.10.20.0 | /24 | 255.255.255.0 | 10.10.20.1‑10.10.20.254 | 10.10.20.255 | 10.10.20.1 |
| 30 | 10.10.30.0 | /24 | 255.255.255.0 | 10.10.30.1‑10.10.30.254 | 10.10.30.255 | 10.10.30.1 |
| 40 | 10.10.40.0 | /22 | 255.255.252.0 | 10.10.40.1‑10.10.43.254 | 10.10.43.255 | 10.10.40.1 |
| 50 | 10.10.50.0 | /23 | 255.255.254.0 | 10.10.50.1‑10.10.51.254 | 10.10.51.255 | 10.10.50.1 |
| 60 | 10.10.60.0 | /24 | 255.255.255.0 | 10.10.60.1‑10.10.60.254 | 10.10.60.255 | 10.10.60.1 |
| 70 | 10.10.70.0 | /24 | 255.255.255.0 | 10.10.70.1‑10.10.70.254 | 10.10.70.255 | 10.10.70.1 |

* **Gateway placement** – Each VLAN’s L3 interface lives on the core router or Layer‑3 switch. The first usable address (e.g., 10.10.10.1) is reserved for the default gateway.  
* **DHCP scopes** – Use a separate DHCP server per VLAN (or a DHCP relay) to avoid cross‑VLAN address leakage. Reserve static IPs for servers, firewalls, and network appliances at the low end of each range (e.g., .10‑.20).

| 10 | fd00:abcd:1234:10::/64 | /64 | fd00:abcd:1234:10::1 |
| 20 | fd00:abcd:1234:20::/64 | /64 | fd00:abcd:1234:20::1 |
| … | … | … | … |

All IPv6 subnets are /64 per RFC 4291, enabling SLAAC and DHCPv6 as needed.

## 4. Firewall Architecture & Rules  

### 4.1 Placement  

| Layer | Device | Reason |
|------|--------|--------|
| **Perimeter** | Next‑generation firewall (NGFW) at ISP edge | External threat inspection, NAT, DoS mitigation |
| **Internal (East‑West)** | Inline firewall or L3 switch with zone‑based ACLs between VLANs (e.g., between **CORP** and **DC**) | Lateral movement control |
| **DMZ** | Separate firewall segment for public‑facing services (web, mail) | Isolate Internet‑exposed assets |

A **three‑tier** model is recommended:

1. **External Zone** – Internet ↔ Perimeter firewall.  
2. **DMZ Zone** – Public services (Web, VPN terminator).  
3. **Internal Zone** – All corporate VLANs, further subdivided into **Trust** (CORP, VOICE) and **Restricted** (MGMT, DEV).

### 4.2 Default‑Deny Posture  

* **Inbound** – Block all traffic from the Internet except explicitly allowed services (HTTPS, VPN).  
* **Outbound** – Block all traffic from internal VLANs except required destinations (e.g., CORP → Internet for web, DNS, NTP).  
* **East‑West** – Deny inter‑VLAN traffic unless a business need is documented (e.g., VOICE ↔ CORP for phone provisioning).  

### 4.3 Sample Rule Set (Vendor‑Neutral Syntax)  

| # | Source Zone | Destination Zone | Protocol/Port | Action | Comment |
|---|-------------|------------------|---------------|--------|---------|
| 1 | **Internet** | **DMZ‑WEB** | TCP/443, TCP/80 | **Allow** | Public web servers |
| 2 | **Internet** | **DMZ‑VPN** | UDP/500, UDP/4500, ESP | **Allow** | IPsec site‑to‑site & remote‑user |
| 3 | **Internet** | **DMZ‑MAIL** | TCP/25, TCP/587 | **Allow** | Inbound mail relay |
| 4 | **DMZ‑WEB** | **Internal‑CORP** | TCP/443 | **Deny** | Prevent web server from reaching corporate LAN |
| 5 | **Internal‑CORP** | **Internet** | TCP/80, TCP/443, UDP/53, UDP/123 | **Allow** | Standard outbound traffic |
| 6 | **Internal‑CORP** | **Internal‑DC** | TCP/1433, TCP/3306, TCP/22 | **Allow** | Application‑to‑DB and admin SSH |
| 7 | **Internal‑VOICE** | **Internal‑CORP** | UDP/5060, TCP/5061 | **Allow** | SIP signaling |
| 8 | **Internal‑MGMT** | **Internet** | TCP/443 | **Allow** | Remote management console (outbound only) |
| 9 | **Internal‑MGMT** | **Internal‑DC** | TCP/22, TCP/443 | **Allow** | Admin access to servers |
|10 | **Any** | **Any** | **All** | **Deny** | Implicit deny (log) |

* **Logging** – Enable logging on all deny rules and on any allow rule that traverses a security zone boundary.  
* **Stateful inspection** – The firewall must track TCP/UDP sessions; only the first packet is evaluated against the rule set.  

### 4.4 NAT Considerations  

| Direction | NAT Type | Example |
|-----------|----------|---------|
| **Outbound (Internal → Internet)** | Dynamic PAT (Port‑Address Translation) | 10.10.0.0/16 → Public IP pool 203.0.113.0/24 |
| **Inbound (Internet → DMZ)** | Static 1:1 NAT for public servers | 203.0.113.10 ↔ 10.10.40.10 (Web Server) |
| **VPN termination** | No‑NAT (or NAT‑exempt) for traffic destined to internal subnets | Traffic from remote site to 10.10.0.0/16 bypasses PAT |

### 4.5 East‑West Filtering  

* Deploy **micro‑segmentation** using firewall policies or software‑defined networking (SDN) to restrict traffic between **CORP** and **DC** to only required ports (e.g., 443 for web services, 3306 for MySQL).  
* Use **zone‑based firewalls** on the core L3 switch for high‑performance intra‑site filtering (e.g., Cisco’s Zone‑Based Policy Firewall, Juniper’s Zone‑Based Forwarding).

## 5. VPN & Remote Access  

### 5.1 Use Cases  

| Scenario | Type | Typical Users |
|----------|------|----------------|
| **Site‑to‑Site** | IPsec tunnel between corporate campus and remote branch | 2‑3 remote sites, each with 10‑30 users |
| **Remote‑User** | SSL‑VPN or IPsec client for telecommuters | 100‑150 mobile/remote employees |
| **Partner Access** | Dedicated IPsec tunnel with limited subnets | External vendors, limited to specific services |

### 5.2 Protocol & Cryptography Choices  

| Component | Recommended Setting |
|-----------|---------------------|
| **IKE version** | IKEv2 (RFC 7296) – better NAT‑traversal, faster re‑keying |
| **Encryption** | AES‑256‑GCM (or AES‑256‑CBC with SHA‑256 HMAC) |
| **Diffie‑Hellman** | Group 14 (2048‑bit) or higher (Group 19 – 256‑bit ECC) |
| **Authentication** | X.509 certificates for both ends (PKI) + optional pre‑shared key (PSK) for legacy devices |
| **Perfect Forward Secrecy (PFS)** | Enabled, same DH group as IKE |
| **Lifetime** | IKE SA 24 h, IPsec SA 1 h (re‑keyed automatically) |
| **NAT‑Traversal** | Enabled (UDP‑500/4500) |

### 5.3 Sample IPsec Site‑to‑Site Configuration (Vendor‑Neutral)  

Below is a **pseudo‑configuration** that can be translated to Cisco IOS, Juniper Junos, Palo Alto PAN‑OS, or Fortinet FortiOS.

```text
# ---------- IKE Phase 1 ----------
crypto ikev2 proposal IKE-PROPOSAL
   encryption aes256-gcm
   integrity sha256
   dh-group 14
   lifetime 86400          ! 24h

crypto ikev2 policy IKE-POLICY
   match fvrf any
   proposal IKE-PROPOSAL

crypto ikev2 keyring KEYRING-REMOTE
   peer REMOTE-SITE
      address 203.0.113.45
      pre-shared-key <redacted>   ! or use certificate

# ---------- IPsec Phase 2 ----------
crypto ipsec transform-set ESP-AES256-GCM esp-aes-256-gcm
   mode tunnel

crypto ipsec profile IPSEC-PROFILE
   set pfs group14
   set transform-set ESP-AES256-GCM
   set ikev2-profile IKE-POLICY

# ---------- Tunnel Interface ----------
interface Tunnel0
   description "Site-to-Site to Remote Office"
   ip address 10.255.255.1 255.255.255.252
   tunnel source GigabitEthernet0/0
   tunnel destination 203.0.113.45
   tunnel mode ipsec ipv4
   tunnel protection ipsec profile IPSEC-PROFILE
   ip mtu 1400
   ip tcp adjust-mss 1360
```

* **Routing** – Advertise the remote site’s internal subnets (e.g., 10.20.0.0/16) via static routes or a dynamic protocol (OSPF/ BGP) over the tunnel.  
* **Failover** – Pair two tunnels (primary/secondary) with different ISP links; use BGP MED/AS‑PATH prepending for traffic engineering.

### 5.4 Remote‑User SSL‑VPN (Example)  

| Component | Recommended Setting |
|-----------|---------------------|
| **Gateway** | SSL‑VPN portal on the perimeter firewall (HTTPS 443) |
| **Client** | Any modern browser or native client (e.g., OpenVPN, AnyConnect) |
| **Authentication** | Multi‑factor (RADIUS + OTP/TOTP) |
| **Split‑Tunnel** | Enabled – only corporate subnets (10.10.0.0/16) are sent through the tunnel |
| **Endpoint Security** | Post‑connect posture check (AV, OS version) |
| **Logging** | Full session logs, user‑to‑IP mapping, and data‑exfiltration alerts |

**Sample OpenVPN client config (inline with TLS‑auth):**

```conf

proto udp
remote vpn.corp.example.com 1194

nobind
persist-key
persist-tun

<ca>
# Insert CA certificate here
</ca>
<cert>
# Insert client certificate
</cert>
<key>
# Insert client private key
</key>
```

## 6. Network Monitoring & Observability  

A robust observability stack gives you **real‑time visibility**, **historical analytics**, and **automated alerting**.

### 6.1 Core Telemetry Sources  

| Source | Protocol | Typical Use |
|--------|----------|-------------|
| **SNMP v3** | UDP/161 (encrypted) | Device health, interface counters, syslog integration |
| **NetFlow / sFlow** | UDP/2055 (NetFlow) or UDP/6343 (sFlow) | Traffic volume, top talkers, application identification |
| **Syslog** | UDP/TCP 514 (prefer TCP/TLS) | Event logs, firewall alerts, authentication failures |
| **Telemetry (gRPC/RESTCONF)** | gRPC, HTTPS | Real‑time streaming of counters (Cisco Model‑Driven Telemetry, Juniper Junos Telemetry) |
| **IP SLA / BFD** | ICMP/UDP | Path latency, link health, fast failure detection |

### 6.2 Monitoring Architecture  

```
[Devices] → (SNMP/NetFlow/sFlow) → [Collector] → [Time‑Series DB] → [Dashboard (Grafana/Chronograf)]
[Devices] → (Syslog) → [Log Aggregator (ELK/Graylog)] → [Search & Alerting]
[Core Switches] → (Telemetry) → [Streaming Processor (Kafka/Fluentd)] → [Analytics Engine]
```

* **Collector** – Use open‑source tools (e.g., **Prometheus Node Exporter**, **ntopng**, **nfdump**) or commercial platforms (SolarWinds, Splunk).  
* **Retention** – Keep 90 days of high‑resolution metrics (1‑minute) and 2 years of aggregated data (hourly).  

### 6.3 Example Monitoring Table  

| Metric | Source | Collection Interval | Alert Threshold | Action |
|--------|--------|---------------------|-----------------|--------|
| Interface Utilization (Tx/Rx) | SNMP ifHCInOctets/ifHCOutOctets | 30 s | > 80 % for 5 min | Generate warning; > 90 % → create ticket |
| CPU Utilization (Core Switch) | SNMP hrProcessorLoad | 30 s | > 85 % for 2 min | Auto‑scale (if LACP) or investigate |
| NetFlow Top Talkers | NetFlow collector | 1 min | Single host > 30 % of total traffic | Trigger security investigation |
| VPN Tunnel Up/Down | SNMP/Telemetry (tunnel status) | 15 s | Tunnel down > 1 min | Auto‑failover to secondary ISP |
| BGP Session State | BGP telemetry | 30 s | Session down > 30 s | Raise critical alert, run failover script |
| Syslog – Authentication Failure | Log aggregator | Real‑time | > 10 failures from same IP in 5 min | Block IP via firewall (dynamic ACL) |
| Temperature (Device) | SNMP environmental MIB | 5 min | > 75 °C | Open ticket for HVAC check |

### 6.4 Alerting & Incident Response  

* **Alert channels** – Email, Slack/Teams webhook, PagerDuty.  
* **Severity mapping** –  
  * **Critical** – Service outage (VPN down, BGP loss).  
  * **High** – Performance degradation (link > 90 % utilization).  
  * **Medium** – Security events (multiple auth failures).  
  * **Low** – Routine warnings (CPU 70 %).  

* **Runbooks** – Store step‑by‑step remediation procedures in a version‑controlled repository (e.g., Git). Include commands for interface checks, BGP troubleshooting, and firewall rule verification.

## 7. High Availability & Failover  

### 7.1 Redundant Physical Links  

| Device Pair | Redundancy Method | Example Config |
|------------|-------------------|----------------|
| Core ↔ Distribution | **LACP (802.3ad)** port‑channel (4 × 10 GbE) | `channel-group 1 mode active` |
| Distribution ↔ Access | **MLAG** (Multi‑Chassis LAG) or **VSS** | Provides active‑active links without STP blocking |
| Core ↔ ISP | Dual ISP routers with **BGP** multi‑homed | ISP‑A AS 64512, ISP‑B AS 64513 |
| Firewall ↔ Core | **Active/Passive** pair with **VRRP** (Virtual Router Redundancy Protocol) | Virtual IP 10.10.0.254 shared by both firewalls |

### 7.2 Spanning Tree Protocol (STP)  

* **Rapid PVST+** (or **MST**) for fast convergence (< 1 s).  
* **Root Bridge** – Place the core switch as the primary root; configure a secondary root on the distribution layer for resilience.  

```text
spanning-tree mode rapid-pvst
spanning-tree vlan 10,20,30,40 priority 4096   ! Core as primary root
spanning-tree vlan 10,20,30,40 priority 8192   ! Distribution as secondary
```

### 7.3 Link Aggregation (LACP)  

* **LACP** provides automatic detection of link failures and load‑balancing based on source/destination MAC/IP.  
* **Hash algorithm** – Use **src‑dest‑IP** for better distribution of server traffic.  

### 7.4 First‑Hop Redundancy (FHR)  

| Protocol | Use Case |
|----------|----------|
| **VRRP/HSRP** | Redundant default gateway for end‑hosts (e.g., VLAN 10 gateway 10.10.10.1/254). |
| **GLBP** | Load‑balancing of default gateway across multiple routers (optional). |
| **CARP** (BSD) | Open‑source alternative for VRRP. |

**Sample VRRP configuration (router‑agnostic):**

```text
interface Vlan10
   ip address 10.10.10.1/24
   vrrp 10 ip 10.10.10.254
   vrrp 10 priority 120
   vrrp 10 preempt
```

### 7.5 HA for VPN  

* **Dual VPN concentrators** in active/passive mode, sharing a virtual IP (VIP) advertised via VRRP.  
* **IPsec re‑keying** is transparent; both peers maintain identical SA parameters.  

### 7.6 HA Testing  

| Test | Frequency | Success Criteria |
|------|-----------|-------------------|
| **Link failover (LACP)** | Quarterly | Convergence < 2 s, no packet loss |
| **VRRP failover** | Monthly (manual) | New master assumes traffic within 1 s |
| **BGP session failover** | Bi‑monthly | Alternate ISP takes traffic without packet loss |
| **VPN tunnel failover** | Quarterly | Secondary tunnel becomes active within 30 s |
| **Firewall HA switchover** | Quarterly (simulated) | No session drops for existing connections (stateful failover) |

## 8. Security Hardening & Operational Best Practices  

### 8.1 Segmentation & Zero‑Trust Principles  

1. **Micro‑segment** critical assets (e.g., DB servers) into their own VLAN/subnet with strict firewall rules.  
2. **East‑west inspection** – Deploy host‑based IDS/IPS or network‑based sensors in each segment.  
3. **Least‑privilege ACLs** – Only allow required ports/protocols; deny everything else.  

### 8.2 Access Control  

| Control | Implementation |
|---------|----------------|
| **802.1X Port‑Based Authentication** | RADIUS backend, certificate‑based for corporate devices, password for BYOD. |
| **Role‑Based Access Control (RBAC)** | Separate admin accounts for network, security, and operations teams. |
| **Privileged Access Management (PAM)** | One‑time passwords for console/SSH access, session recording. |
| **Network‑Level ACLs** | Apply on firewall and L3 switches; use object groups for maintainability. |

### 8.3 Change Management  

* **Version control** – Store all device configurations in Git (or similar).  
* **CI/CD pipeline** – Use Ansible playbooks to push changes after automated linting (e.g., `ansible-lint`).  
* **Change Advisory Board (CAB)** – Review major topology or policy changes; require at least two approvals.  
* **Rollback plan** – Keep previous configuration snapshots; automate rollback if health checks fail.  

### 8.4 Auditing & Compliance  

| Activity | Tool | Frequency |
|----------|------|-----------|
| **Configuration audit** | NCM (Network Configuration Manager) or open‑source `rancid` | Daily diff, weekly report |
| **Vulnerability scanning** | Nessus, OpenVAS | Monthly |
| **Patch management** | Vendor advisory feed, automated OS upgrade scripts | Quarterly |
| **Log retention** | Central log server (ELK) | 1 year (PCI‑DSS) or as required |
| **User access review** | IAM reports | Quarterly |

### 8.5 Hardening Checklist (Vendor‑Neutral)  

| Item | Recommended Setting |
|------|----------------------|
| **Management plane** | SSH only, disable Telnet; use strong ciphers (AES‑256, SHA‑2). |
| **SNMP** | v3 with authentication and encryption; disable v1/v2c. |
| **NTP** | Authenticated NTP (NTPv4 with symmetric keys). |
| **Syslog** | TLS‑encrypted transport to central collector. |
| **Password policy** | Minimum 12 characters, complexity, rotation every 180 days. |
| **Banner** | Legal disclaimer on all device consoles. |
| **IP source guard / DHCP snooping** | Enable on access ports to prevent IP spoofing. |
| **Dynamic ARP inspection (DAI)** | Enable on VLANs with DHCP snooping. |
| **Port security** | Limit MAC addresses per port (e.g., 2 for workstations, 1 for servers). |
| **Loop protection** | Enable BPDU Guard on edge ports, Root Guard on uplinks. |
| **QoS** | Classify voice (VLAN 30) with DSCP 46, guarantee bandwidth. |
| **Backup** | Automated daily configuration backup to off‑site storage. |

### 8.6 Incident Response Workflow  

1. **Detect** – Alert from monitoring system (e.g., abnormal traffic spike).  
2. **Triage** – Verify scope, identify affected VLANs/subnets.  
3. **Contain** – Apply temporary ACLs or quarantine the offending host.  
4. **Eradicate** – Remove malicious artifacts, patch vulnerable services.  
5. **Recover** – Restore normal ACLs, verify service health.  
6. **Post‑mortem** – Document root cause, update policies, and run a lessons‑learned session.

**Key take‑aways**

* **Segmentation first** – VLANs and subnets are the backbone of security and performance.  
* **Default‑deny everywhere** – From the perimeter to east‑west traffic, start with “deny all” and add explicit permits.  
* **Automation matters** – Use IaC (Infrastructure as Code) for repeatable, auditable deployments.  
* **Observability is continuous** – Real‑time telemetry, proper alert thresholds, and regular health checks keep the network resilient.  
* **Document, test, repeat** – Every change should be versioned, reviewed, and validated through failover drills.

By following the structured approach outlined above, a mid‑size enterprise can achieve a **secure, high‑performing, and resilient campus network** that scales for future growth (IoT, cloud integration, and remote work) while meeting compliance and operational excellence standards.

**Appendix – Glossary (selected)**  

| Term | Definition |
|------|------------|
| **VLAN** | Virtual LAN – a Layer‑2 broadcast domain created via 802.1Q tagging. |
| **LACP** | Link Aggregation Control Protocol – IEEE 802.3ad for bundling multiple physical links. |
| **VRRP** | Virtual Router Redundancy Protocol – provides a shared virtual IP for gateway redundancy. |
| **IPsec** | Suite of protocols (IKE, ESP, AH) for securing IP traffic. |
| **NetFlow / sFlow** | Flow‑export technologies for traffic analysis. |
| **BGP** | Border Gateway Protocol – used for inter‑autonomous system routing (e.g., multi‑ISP). |
| **MPLS** | Multi‑Protocol Label Switching – not covered here but often used for WAN. |
| **Zero‑Trust** | Security model that assumes no implicit trust, verifies every request. |
