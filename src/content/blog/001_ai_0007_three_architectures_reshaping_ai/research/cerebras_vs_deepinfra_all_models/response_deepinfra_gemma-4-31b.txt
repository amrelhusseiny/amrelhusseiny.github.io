# Enterprise Network Infrastructure Design Guide (Mid-Size Enterprise)

## Executive Summary
This guide outlines the architectural standards for a mid-size enterprise supporting approximately 500 employees. The design focuses on the "Three-Tier Hierarchical Model" (Core, Distribution, and Access) to ensure scalability, deterministic traffic patterns, and high availability. The primary objective is to minimize the blast radius of security breaches through rigorous segmentation and to ensure 99.99% uptime through hardware and logical redundancy.

---

## 1. VLAN Design and Segmentation

### 1.1 The Philosophy of Segmentation
In a 500-user environment, a "flat" network (single Layer 2 domain) is untenable. Large broadcast domains lead to excessive ARP traffic, "broadcast storms," and an inability to contain security threats. Segmentation serves two primary purposes:
1.  **Performance:** Limiting broadcast domains reduces CPU overhead on end-user devices and minimizes network congestion.
2.  **Security:** By isolating traffic into VLANs, we can enforce "Least Privilege" access at the Layer 3 boundary (Firewall or Core Switch), preventing an infected workstation in Marketing from accessing the HR database.

### 1.2 Logical Grouping Strategy
Devices should be grouped by **function and security requirement**, not necessarily by physical location. A user in Building A and Building B should both be on the "Corporate Data" VLAN if they share the same access requirements.

#### Recommended VLAN Assignments
| VLAN ID | Name | Description | Priority/QoS |
| :--- | :--- | :--- | :--- |
| 10 | MGMT_NET | Network Device Management (SSH, SNMP) | High |
| 20 | CORP_DATA | Standard Employee Workstations (Wired) | Medium |
| 30 | CORP_WIFI | Corporate Laptops/Mobile (802.1X) | Medium |
| 40 | VOIP_PHONES | Voice over IP Traffic | Critical |
| 50 | GUEST_WIFI | Isolated Guest Internet Access | Low |
| 60 | IOT_BUILDING | HVAC, Cameras, Badge Readers | Low |
| 70 | SERVER_DMZ | Public-facing services | Medium |
| 80 | SERVER_INT | Internal Application/Database Servers | High |
| 90 | SECURITY_CAM | High-bandwidth CCTV traffic | Medium |
| 999 | BLACKHOLE | Unused ports (Dead VLAN) | N/A |

### 1.3 Implementation Notes
*   **The Native VLAN:** Never use VLAN 1 for data traffic. Change the native VLAN on all trunks to a non-routed VLAN (e.g., VLAN 999) to mitigate VLAN hopping attacks.
*   **Pruning:** Use VTP pruning or manual trunk allowed lists to ensure VLAN traffic only travels where it is required.

## 2. IP Addressing and Subnetting

### 2.1 Addressing Strategy
For a 500-employee site, the `10.0.0.0/8` private range (RFC 1918) provides the necessary flexibility. We will use a `/20` block for the campus to allow for future growth and site expansion.

**Campus Block:** `10.10.0.0/20` (Range: `10.10.0.0` - `10.10.15.255`)

### 2.2 Subnet Mapping Table
We utilize Variable Length Subnet Masking (VLSM) to allocate space efficiently. High-density areas (Wi-Fi) receive larger blocks, while management networks receive smaller ones.

| VLAN | Subnet | Mask | CIDR | Usable IPs | Purpose |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 10 | 10.10.0.0 | 255.255.255.0 | /24 | 254 | Network Management |
| 20 | 10.10.1.0 | 255.255.252.0 | /22 | 1022 | Corporate Wired |
| 30 | 10.10.5.0 | 255.255.252.0 | /22 | 1022 | Corporate Wireless |
| 40 | 10.10.9.0 | 255.255.255.0 | /24 | 254 | VoIP |
| 50 | 10.10.10.0 | 255.255.252.0 | /22 | 1022 | Guest WiFi |
| 60 | 10.10.14.0 | 255.255.255.0 | /24 | 254 | IoT/Building |
| 70 | 10.10.15.0 | 255.255.255.128 | /25 | 126 | DMZ Servers |
| 80 | 10.11.0.0 | 255.255.255.0 | /24 | 254 | Internal Servers |

### 2.3 Gateway Design
The Default Gateway for each VLAN will reside on the Core Switch (SVI - Switch Virtual Interface) or the Firewall, depending on the security requirement. 
*   **Internal routing:** Handled by the Core Switch for performance.
*   **Inter-VLAN security:** Critical traffic (e.g., Guest $\to$ Internal) is routed through the Firewall.

## 3. Firewall Architecture and Rules

### 3.1 Deployment Model
A **"Zone-Based" Firewall (ZBF)** architecture is required. Rather than thinking in terms of interfaces, we group interfaces into security zones:
*   **WAN Zone:** External Internet.
*   **DMZ Zone:** Public servers.
*   **Trusted Zone:** Internal corporate VLANs.
*   **Untrusted Zone:** Guest and IoT networks.

### 3.2 The "Default-Deny" Posture
The fundamental rule of the firewall is an **Implicit Deny**. All traffic is blocked unless a specific permit rule exists. This prevents "leakage" and ensures that new services cannot be launched without security review.

### 3.3 East-West Filtering
Traditional firewalls focus on North-South traffic (Internet $\to$ Internal). However, most modern attacks move laterally (East-West). To mitigate this:
1.  **Micro-segmentation:** Use the firewall to inspect traffic moving between internal VLANs (e.g., VLAN 20 $\to$ VLAN 80).
2.  **VLAN Access Control Lists (VACLs):** For high-speed filtering within a VLAN.

### 3.4 Example Rule Set
| Rule ID | Source Zone | Dest Zone | Service/Port | Action | Logic |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 101 | Trusted | WAN | HTTP/S (80, 443) | PERMIT | Allow web browsing |
| 102 | WAN | DMZ | HTTP/S (80, 443) | PERMIT | Allow public web access |
| 103 | DMZ | Trusted | SQL (1433) | PERMIT | Allow DMZ App $\to$ DB Server |
| 104 | Untrusted | WAN | HTTP/S (80, 443) | PERMIT | Guest Internet only |
| 105 | Untrusted | Trusted | ANY | **DENY** | Block Guest $\to$ Internal |
| 106 | ANY | ANY | ANY | **DENY** | Implicit Deny All |

## 4. VPN and Remote Access

### 4.1 Remote Access VPN (Client-to-Site)
For 500 employees, a **SSL/TLS VPN** (such as OpenVPN or AnyConnect) is the standard.
*   **Authentication:** Integration with Active Directory (AD) via RADIUS or LDAP.
*   **MFA:** Multi-Factor Authentication (TOTP or Push notifications) is mandatory for all VPN entries.
*   **Encryption:** AES-256-GCM for data encryption and SHA-384 for hashing.

### 4.2 Site-to-Site VPN
Used for connecting branch offices or cloud VPCs.
*   **Protocol:** IPsec (Internet Protocol Security).
*   **Phase 1 (IKEv2):** AES-256, DH Group 14 or higher.
*   **Phase 2 (ESP):** AES-GCM for authenticated encryption.

### 4.3 Sample Configuration Logic (Pseudo-Config)
```bash
# IKEv2 Proposal
crypto ikev2 proposal VPN_PROP 
 encryption aes-256-gcm 
 prf sha384 
 group 14

# IPsec Profile
crypto ipsec profile SITE_TO_SITE_PROFILE
 set transform-set ESP-AES-GCM
 set pfs group14

# Tunnel Interface
interface Tunnel0
 ip address 10.20.0.1 255.255.255.252
 tunnel source WAN_INTERFACE
 tunnel destination [Remote_Public_IP]
 tunnel protection ipsec profile SITE_TO_SITE_PROFILE
```

## 5. Network Monitoring and Observability

### 5.1 Telemetry Layers
A "single pane of glass" approach is required to avoid alert fatigue.

#### A. SNMP (Simple Network Management Protocol)
*   **Use Case:** Device health (CPU, RAM, Interface status).
*   **Version:** SNMPv3 only (v1/v2 send community strings in cleartext).
*   **Polling:** 5-minute intervals for standard metrics; 1-minute for critical links.

#### B. Flow Telemetry (NetFlow/sFlow)
*   **Use Case:** Traffic analysis. "Who is talking to whom and how much?"
*   **Implementation:** Enabled on the Core Switch and Firewall.
*   **Analysis:** Export flows to a collector (e.g., Plixer, PRTG, or ELK Stack) to identify top talkers and DDoS patterns.

#### C. Logging (Syslog)
*   **Use Case:** Auditing and forensics.
*   **Configuration:** Centralized Syslog server. Level "Informational" for edges; "Warning" and "Error" for core.

### 5.2 Alerting Thresholds
To prevent "noise," thresholds must be tiered:
*   **Critical (Immediate Page):** Interface Down (Core), BGP Neighbor Loss, Firewall Failover.
*   **Warning (Ticket Created):** CPU > 70% for 15 mins, Memory > 80%, CRC errors on a port.
*   **Info (Log Only):** User VPN Login/Logout.

## 6. High Availability and Failover

### 6.1 Physical Redundancy
*   **Dual-Homing:** Every Access switch must have two uplinks (one to each Distribution switch).
*   **LACP (Link Aggregation):** Use 802.3ad (LACP) to bundle multiple physical links into a single logical "Port-Channel." This provides both increased bandwidth and instant failover if one cable is severed.

### 6.2 Layer 2 Loop Prevention
*   **Rapid Spanning Tree Protocol (RSTP):** Standardized via 802.1w to ensure convergence in < 2 seconds.
*   **BPDU Guard:** Enabled on all "Edge" ports (where PCs connect) to prevent users from plugging in unauthorized switches and creating loops.

### 6.3 First Hop Redundancy (FHRP)
To prevent the Default Gateway from being a single point of failure, implement **HSRP (Hot Standby Router Protocol)** or **VRRP (Virtual Router Redundancy Protocol)**.
*   Two switches share a "Virtual IP" (VIP).
*   If the Primary switch fails, the Standby switch assumes the VIP in milliseconds.

| Device | Physical IP | Virtual IP (Gateway) | Priority |
| :--- | :--- | :--- | :--- |
| Core-01 | 10.10.1.2 | 10.10.1.1 | 110 (Active) |
| Core-02 | 10.10.1.3 | 10.10.1.1 | 100 (Standby) |

## 7. Security Hardening and Best Practices

### 7.1 Switchport Hardening
The Access Layer is the most vulnerable point of the network.
*   **Port Security:** Limit the number of MAC addresses per port to 1 or 2. Shutdown the port if a violation occurs.
*   **DHCP Snooping:** Prevent "Rogue DHCP servers" from handing out incorrect IP addresses.
*   **Dynamic ARP Inspection (DAI):** Prevent ARP spoofing/Man-in-the-Middle attacks.

### 7.2 Management Plane Security
*   **Out-of-Band (OOB) Management:** Use a dedicated physical network for management ports to ensure access even during a broadcast storm.
*   **SSH only:** Disable Telnet and HTTP management. Force SSHv2 with RSA keys.
*   **TACACS+ / RADIUS:** Never use a shared "admin" password. All engineers must authenticate with individual credentials.

### 7.3 Change Management and Auditing
Technical excellence is negated by poor process.
1.  **The Golden Config:** Maintain a version-controlled backup of all configurations (e.g., using Oxidized or Rancid).
2.  **Change Windows:** All changes must follow a *Request $\to$ Review $\to$ Test $\to$ Implement $\to$ Verify* workflow.
3.  **Audit Trail:** All CLI commands should be logged via TACACS+ to identify who changed what and when.

### 7.4 Summary Checklist for Deployment
- [ ] All unused ports assigned to VLAN 999 and shut down.
- [ ] LACP configured on all inter-switch links.
- [ ] RSTP BPDU Guard active on all edge ports.
- [ ] Firewall "Default Deny" rule verified at the bottom of the set.
- [ ] MFA enabled for all VPN and Administrative access.
- [ ] SNMPv3 and NetFlow exporting to the monitoring server.
- [ ] FHRP (VRRP/HSRP) tested via manual failover of the primary core.
