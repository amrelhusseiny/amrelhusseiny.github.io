# Comprehensive Network Infrastructure Guide for Mid-Size Enterprise

## Executive Summary

Designing a network infrastructure for a mid-size enterprise (approximately 500 employees) requires a delicate balance between scalability, security, performance, and operational manageability. At this scale, the "flat network" of small businesses is no longer sufficient; conversely, the excessive complexity of carrier-grade architectures is often cost-prohibitive.

This guide outlines a robust, modular, and secure network design. It assumes a hierarchical model (Core, Distribution, Access) leveraging Layer 3 switching for routing and Layer 2 switching for endpoint connectivity. The design prioritizes segmentation for security, high availability for business continuity, and observability for rapid troubleshooting.

---

## 1. VLAN Design and Segmentation

Virtual LANs (VLANs) are the fundamental building blocks of logical network segmentation. For a 500-user environment, VLANs serve two critical purposes: **containment of broadcast domains** and **enforcement of security boundaries**.

### The Strategy: Functional Segmentation
We will group devices based on their function and trust level rather than physical location. This ensures that a compromised intern PC in Sales cannot easily broadcast to the Finance servers or the Guest Wi-Fi.

*   **Broadcast Control:** Without VLANs, a single 500-user network would be saturated with Address Resolution Protocol (ARP), Bonjour/mDNS, and DHCP broadcast traffic.
*   **Security Segmentation:** By isolating device classes, we can apply Access Control Lists (ACLs) or Firewall rules between these groups. This is the foundational step toward a Zero Trust architecture.

### VLAN ID Assignment
We will use the 802.1Q standard for trunking. To allow for future growth, we will assign gaps in the numbering scheme.

| VLAN ID | Name | Description | Subnet (Example) |
| :--- | :--- | :--- | :--- |
| 10 | MGMT | Network Device Management (OOB) | 10.10.0.0/24 |
| 20 | NATIVE | Native VLAN (Unused for data) | N/A |
| 100 | DATA_USERS | Corporate Workstations | 10.10.10.0/24 |
| 110 | DATA_PRINT | Network Printers | 10.10.11.0/24 |
| 120 | VOICE | VoIP Phones & UC Servers | 10.10.12.0/24 |
| 130 | SERVERS | Internal Data Center / Server Farm | 10.10.20.0/24 |
| 140 | IOT | Building Management, HVAC, Cameras | 10.10.30.0/24 |
| 150 | GUEST | Isolated Guest Wi-Fi | 10.10.50.0/24 |
| 999 | BLACKHOLE | Null route VLAN for DDoS mitigation | N/A |

### Design Notes
1.  **Voice VLAN (120):** Configured with a higher CoS (Class of Service) value (e.g., 5) to prioritize QoS.
2.  **Native VLAN (20):** We explicitly change the native VLAN from the default (VLAN 1) to an unused ID (VLAN 20) and "prune" it from all trunks to prevent VLAN hopping attacks.
3.  **IoT Segmentation (140):** IoT devices are notoriously insecure. This VLAN is heavily firewalled; it is allowed only DNS/HTTPs to the internet and specific communication to the management server, but no direct access to the DATA_USER VLAN.

## 2. IP Addressing and Subnetting

A structured IP addressing plan simplifies routing, summarization, and troubleshooting. We will utilize private RFC1918 addressing (Class A: 10.0.0.0/8) to provide ample room for expansion.

### Subnetting Philosophy
We employ **Variable Length Subnet Masking (VLSM)**.
*   **User Subnets:** `/24` (254 usable hosts). This fits the 500 employees across different departments easily without wasting IPs or requiring large subnets that increase broadcast traffic.
*   **Server Subnets:** `/24` or `/23`. Allows for high density of virtual machines and physical servers.
*   **Point-to-Point Links:** `/30` or `/31`. Used for router-to-router or Layer 3 switch links to conserve address space.
*   **Loopback Interfaces:** `/32`. Used for management and OSPF/BGP router IDs.

### Campus Addressing Plan
The 10.10.x.x octet is reserved for the primary campus site.

| Usage | VLAN | Network Address | Subnet Mask | Gateway IP | Usable Hosts Range | Broadcast |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Management | 10 | 10.10.0.0 | 255.255.255.0 | .1 | 10.10.0.2 - .254 | .255 |
| Data Users | 100 | 10.10.10.0 | 255.255.255.0 | .1 | 10.10.10.2 - .254 | .255 |
| Printers | 110 | 10.10.11.0 | 255.255.255.0 | .1 | 10.10.11.2 - .254 | .255 |

### DNS and DHCP Strategy
*   **DHCP Scope:** Scopes are defined on central DHCP servers (Microsoft Server or Infoblox). IP Helper addresses (DHCP Relay) are configured on the Layer 3 interfaces (SVIs) on the Core/Distribution switches.
*   **DNS:** Internal AD-integrated DNS servers (10.10.20.10, 10.10.20.11) are handed out to corporate clients. Guest users receive Google DNS (8.8.8.8) or OpenDNS via the Guest gateway.

## 3. Firewall Architecture and Rules

For 500 users, a single firewall at the edge is insufficient. We propose a **Tiered Firewall Architecture**.

### Placement and Topology
1.  **Edge Firewall (The Perimeter):** Sits between the ISP and the Internal Core. Handles NAT, basic filtering, and VPN termination.
2.  **Internal Firewall (East-West):** Sits between the Core Switch and the Server Farm (VLAN 130). This separates high-value assets (databases, finance servers) from general user traffic.

### Default-Deny Posture
All firewalls must operate on a "whitelist" basis. The implicit rule at the bottom of every ACL is `deny any any`.
*   **Inbound:** Deny all, except specific ports (e.g., 443 for public web server).
*   **Outbound:** Allow necessary business traffic, block unauthorized high-risk ports (e.g., 445, 3389) to the internet.
*   **East-West:** Deny inter-VLAN routing by default, then allow specific exceptions.

### Example Rule Set: Edge Firewall (Inbound)

| Rule # | Source | Destination | Service | Action | Logging | Description |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 10 | Any | Public Web Server IP | TCP/443 | Allow | Enabled | HTTPS Traffic |
| 20 | ISP VPN Peer | Firewall WAN IP | UDP/500, 4500 | Allow | Enabled | IKEv2 for VPN |
| 30 | Any | Any | ANY | Deny | Enabled | Default Deny |

## 4. VPN and Remote Access

With a hybrid workforce, secure remote access is mandatory. We utilize **IPsec for Site-to-Site** and **SSL VPN for Remote Access**.

### Cryptography Choices
Avoid legacy cryptography. Use Suite B or NSA-recommended algorithms where possible.
*   **IKE Phase 1:** DH Group 19 or 20 (256-bit ECP), AES-256-GCM, SHA-384.
*   **IPsec Phase 2:** AES-256-GCM (provides encryption and integrity), SHA-384.
*   **PFS:** Perfect Forward Secrecy is mandatory (using DH Group 19+).

### Site-to-Site VPN
Used to connect the main office to branch offices or cloud VPCs (e.g., AWS DirectConnect or Azure VNet Gateway).
*   **Protocol:** IKEv2.
*   **Tunnel Mode:** Used for public internet transport.

### Remote User VPN (SSL VPN)
While IPsec is robust, SSL VPN (Clientless or Thick Client) is easier to traverse through NAT/Firewalls at home/hotels without complex client configuration.
*   **Authentication:** MFA (Multi-Factor Authentication) via RADIUS/DUO.
*   **Split Tunneling:** Configured to only send traffic destined for 10.0.0.0/8 through the VPN. General internet browsing goes out the user's local gateway to preserve corporate bandwidth.

### Sample Configuration Snippet (Vendor-Agnostic)
*Note: This abstract syntax represents common CLI logic found in Cisco, Juniper, or Ubiquiti.*

```text
crypto ikev2 proposal IKE-PROP-STRONG
  encryption aes-cbc-256
  integrity sha384
  group 19
  prf hmac-sha384
  lifetime 86400

crypto ipsec transform-set IPSEC-TSET-STRONG
  esp-aes-256
  esp-sha384-hmac
  mode tunnel
  pfs group19

access-list VPN-TRAFFIC
  permit ip 10.10.0.0 255.255.0.0 192.168.50.0 255.255.255.0
  ! Matches remote office subnet

crypto map OUTSIDE-MAP 10 ipsec-isakmp
  set peer 203.0.113.55
  set transform-set IPSEC-TSET-STRONG
  match address VPN-TRAFFIC

interface GigabitEthernet0/0 (WAN)
  crypto map OUTSIDE-MAP
  ip access-group OUTSIDE-IN in
```

## 5. Network Monitoring and Observability

You cannot secure what you cannot see. For a 500-node network, we need both granular metrics and flow data.

### SNMP (Simple Network Management Protocol)
*   **Version:** Use SNMPv3 only. v1 and v2c transmit community strings in cleartext.
*   **Configuration:** Use `authPriv` (Authentication and Privacy) mode.
    *   Auth Protocol: SHA-256 or SHA-512.
    *   Priv Protocol: AES-128 or AES-256.
*   **Monitoring Targets:** Interface utilization (In/Out octets), CPU load, Memory usage, Temperature/Fan status, Power Supply status.

### Flow Telemetry (NetFlow/sFlow)
SNMP tells you *how much* bandwidth is used; NetFlow tells you *by whom* and *what*.
*   **Technology:** Use **NetFlow v9** or **IPFIX** for Cisco/Juniper gear; **sFlow** for HP/Aruba.
*   **Sampling Rate:** Configure hardware sampling (e.g., 1:1000) on 10G uplinks to reduce CPU impact.
*   **Use Cases:**
    *   Identifying the user consuming the most bandwidth.
    *   Detecting lateral movement (sudden data flow between VLANs that shouldn't communicate).
    *   DDoS detection.

### Logging and Syslog
Centralize logs to a dedicated SIEM (e.g., Splunk, ELK Stack, or Graylog).
*   **Log Levels:**
    *   **Emergencies/Alerts/Critical:** SMS/Pager trigger.
    *   **Errors:** Email ticket generation.
    *   **Informational/Debugging:** Archival and forensic analysis.
*   **NTP Time Sync:** Ensure all network devices sync to a local stratum NTP server. Without accurate time, log correlation is impossible.

### Alerting Thresholds (Example)
*   **CPU:** >80% for 5 minutes (Sustained load).
*   **Interface Error Rate:** >0.1% input errors (indicates cabling issues).
*   **BGP/OSPF:** Neighbor state change (Full -> Down).
*   **Power Supply:** PSU status change (OK -> Failed).

## 6. High Availability and Failover

Downtime is expensive. We design for both equipment failure and link failure.

### Layer 2 Redundancy: LACP and Spanning Tree
*   **LACP (Link Aggregation Control Protocol):** We use 802.3ad LACP port-channels everywhere possible. Access switches have 2x10G or 4x1G LACP trunks to the distribution layer. This increases bandwidth and provides instant failover (sub-second) if a cable breaks.
*   **Spanning Tree Protocol (STP):**
    *   **Variant:** Use **Rapid PVST+** (Cisco) or **RSTP** (Standard). Avoid legacy STP (802.1D) due to slow convergence (50s).
    *   **Root Bridge:** Manually set the Core Distribution switches as the Primary and Secondary Root Bridge to prevent random switches from taking over.
    *   **PortFast:** Enable PortFast/BPDUGuard on all access ports to prevent loops from user devices causing outages.
    *   **BPDU Filter:** Do not use globally; use PortFast edge features carefully.

### Layer 3 Redundancy: FHRP
First-Hop Redundancy Protocols allow two routers/gateways to share a single IP address (the virtual IP).
*   **Protocol:** **VRRP** (Virtual Router Redundancy Protocol) is preferred as it is an open standard. HSRP (Cisco) or GLBP are alternatives.
*   **Configuration:**
    *   **Core Switch A:** VRRP Priority 110 (Master).
    *   **Core Switch B:** VRRP Priority 100 (Backup).
    *   **Preempt:** Enabled on both. If the Master fails and comes back online, it should resume the Master role.
*   **Load Balancing:** Utilize MHSRP (Multiple HSRP groups) or VRRP with separate groups per VLAN to load balance traffic (Core A is Master for even VLANs, Core B for odd VLANs).

### Convergence Technologies
*   **BFD (Bidirectional Forwarding Detection):** Use BFD with your routing protocol (OSPF/BGP) and FHRP. BFD detects link failures in milliseconds (hardware offloaded) rather than seconds, allowing routing reconvergence to happen instantly.

## 7. Security Hardening and Best Practices

The network is the foundation of security. Hardening ensures the infrastructure itself is not a vector for attack.

### Access Control & AAA
*   **Centralized AAA:** All network switches and routers must authenticate admins via a centralized TACACS+ or RADIUS server (e.g., Microsoft NPS or Cisco ISE).
*   **Privilege Levels:** Use specific authorization. Tier 1 admins get read-only; Tier 3 get full exec rights.
*   **Management Plane:**
    *   **Out-of-Band (OOB) Management:** Use a dedicated management VLAN (VLAN 10) and physically separate management ports if possible.
    *   **In-Band ACL:** If OOB is not possible, apply an ACL to the VTY lines permitting only the IT subnet and bastion host IPs.
    *   **SSH:** Disable Telnet. Force SSH version 2.
    *   **HTTPS:** Disable HTTP. Use a valid certificate for the web management UI.

### Physical Security & Unused Ports
*   **Shutdown Unused Ports:** Any interface not connected to a device should be administratively shut down.
*   **Port Security:** Enable `switchport port-security` on access ports.
    *   **Violation Mode:** Restrict or Shutdown (Shutdown is more secure but causes more tickets; Restrict drops the frames).
    *   **MAC Addresses:** Limit 1 or 2 MACs (for VoIP phone + PC).
*   **BPDU Guard:** Enabled on all access ports to prevent users from plugging in switches and becoming the Root Bridge.

### Change Management & Auditing
*   **Configuration Archives:** Use automated tools (SolarWinds, Oxidized, RANCID) to archive configuration backups nightly.
*   **Control Plane Policing (CoPP):** Protect the CPU of the router. Drop packets destined to the CPU for bogus protocols (e.g., IP fragments to the CPU, non-EIGRP packets) to prevent DoS attacks against the infrastructure itself.
*   **Compliance Audits:** Run quarterly scans to verify:
    1.  No default passwords exist.
    2.  No "any any" ACLs exist.
    3.  NTP is configured and correct.
    4.  Logging is active and reaching the SIEM.

### Anti-Spoofing
Enable uRPF (Unicast Reverse Path Forwarding) in strict or loose mode on edge interfaces. This verifies that packets arriving on an interface have a source address reachable via that same interface, preventing IP spoofing.

## Conclusion

This infrastructure design provides a resilient, scalable, and secure foundation for a 500-user enterprise. By adhering to the segmentation strategies, utilizing high-availability protocols like VRRP and LACP, and maintaining a strict default-deny security posture, the network will support current operational needs while remaining adaptable to future growth and threats. Continuous monitoring via NetFlow and centralized logging ensures that the network team maintains visibility into the ever-changing traffic patterns of the organization.
