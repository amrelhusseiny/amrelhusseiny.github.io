# Enterprise Network Infrastructure Configuration Guide: Mid-Size Enterprise (500 Employees)

## Executive Summary
This guide provides a comprehensive technical blueprint for designing and implementing a resilient, secure, and scalable network infrastructure for a mid-size enterprise. The architecture follows the classic hierarchical model (Core, Distribution, Access) and adheres to the principle of **Zero Trust** via strict segmentation and a default-deny security posture.

---

## 1. VLAN Design and Segmentation

### 1.1 The Philosophy of Segmentation
In a 500-employee environment, a single "flat" network is a critical failure point. Segmentation serves two primary purposes:
1.  **Reduction of Broadcast Domains:** By limiting the size of a broadcast domain, we prevent "broadcast storms" and reduce unnecessary CPU interrupts on end-device NICs.
2.  **Security Isolation (Blast Radius):** Segmentation ensures that a compromised device in the Guest Wi-Fi cannot reach the HR server or the Domain Controller.

### 1.2 VLAN Grouping Strategy
Devices should be grouped by **function and trust level**, not necessarily by physical location. This allows for consistent security policies regardless of which switch port a user is plugged into.

| VLAN ID | Name | Description | Trust Level |
| :--- | :--- | :--- | :--- |
| 10 | MGMT_NET | Network infrastructure management (Switches, APs, UPS) | Critical |
| 20 | SERVER_FARM | On-premise servers, AD, DNS, File shares | High |
| 30 | USER_CORP | Corporate employees (Wired/Wireless) | Medium |
| 40 | VOICE_VOIP | VoIP Phones (prioritized via QoS) | Medium |
| 50 | IOT_DEV | Printers, Security Cameras, Smart badges | Low |
| 60 | GUEST_WIFI | Visitor internet access (Isolated) | Zero |
| 99 | NATIVE_BLACKHOLE | Unused ports / Native VLAN for security | N/A |

### 1.3 Implementation Notes
*   **Native VLAN:** Always change the default Native VLAN from 1 to a non-routable ID (e.g., 99) to prevent VLAN hopping attacks.
*   **Pruning:** Manually prune VLANs from trunk links to ensure that VLAN 60 (Guest) traffic does not traverse switches where no guest access is provided.

## 2. IP Addressing and Subnetting

### 2.1 Addressing Scheme
For a 500-employee enterprise, the `10.0.0.0/8` private range is recommended to allow for future growth. We will utilize a `/16` summary block for the campus to keep routing tables clean.

**Campus Summary:** `10.10.0.0/16`

### 2.2 Subnet Allocation Plan
We will use Variable Length Subnet Masking (VLSM) to optimize address space. Most user VLANs are sized at `/23` (510 hosts) to account for multiple devices per user (laptop, phone, tablet).

| VLAN | Subnet | Mask | Gateway | Range | Purpose |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 10 | 10.10.10.0/24 | 255.255.255.0 | 10.10.10.1 | .2 - .254 | Infrastructure Mgmt |
| 20 | 10.10.20.0/24 | 255.255.255.0 | 10.10.20.1 | .2 - .254 | Server Farm |
| 30 | 10.10.32.0/23 | 255.255.254.0 | 10.10.32.1 | .2 - .33.254 | Corporate Users |
| 40 | 10.10.40.0/24 | 255.255.255.0 | 10.10.40.1 | .2 - .254 | VoIP |
| 50 | 10.10.50.0/24 | 255.255.255.0 | 10.10.50.1 | .2 - .254 | IoT / Printers |
| 60 | 10.10.64.0/22 | 255.255.252.0 | 10.10.64.1 | .2 - .67.254 | Guest Wi-Fi |

### 2.3 DHCP Strategy
*   **Centralized DHCP:** Use the Domain Controller or a dedicated Linux DHCP server in VLAN 20.
*   **DHCP Relay:** Configure `ip helper-address` (or equivalent) on the Layer 3 switch (SVI) for each VLAN to forward requests to the central server.

## 3. Firewall Architecture and Rules

### 3.1 Placement and Topography
The firewall should be deployed as the **Gateway of Last Resort** between the Internal Core and the ISP. To handle internal segmentation (East-West traffic), a "Zone-Based" approach is utilized.

**Zones Defined:**
*   **Untrusted:** The Public Internet.
*   **DMZ:** Public-facing servers (Web, Mail relay).
*   **Trusted:** The Internal Core (VLANs 10, 20, 30, 40, 50).
*   **Guest:** VLAN 60 (completely isolated).

### 3.2 Default-Deny Posture
The firewall must be configured with an implicit `deny all` rule at the end of every policy set. Traffic is only permitted if explicitly defined.

### 3.3 Example Rule Set (Simplified)

| Source Zone | Destination Zone | Service/Port | Action | Rationale |
| :--- | :--- | :--- | :--- | :--- |
| Trusted | Untrusted | HTTP/S, DNS, NTP | Permit | General Internet Access |
| Trusted | DMZ | SSH, RDP | Permit | Administering DMZ servers |
| Untrusted | DMZ | 80, 443 | Permit | Public web access |
| Guest | Untrusted | HTTP/S, DNS | Permit | Guest Internet |
| Guest | Trusted | Any | **Deny** | Prevent lateral movement |
| IOT $\to$ Trusted | Server Farm | Print (9100) | Permit | Allow printing to servers |
| Any | MGMT_NET | Any | **Deny** | Isolate management network |

### 3.4 East-West Filtering
For high-security environments, do not rely solely on the perimeter firewall for internal VLAN routing. Implement **Access Control Lists (ACLs)** on the Core Switch SVIs to filter traffic between VLAN 30 (Users) and VLAN 10 (Management) at wire-speed.

## 4. VPN and Remote Access

### 4.1 Remote-User VPN (Client-to-Site)
For the 500-employee workforce, a **SSL-VPN** is recommended over IPsec for client access due to ease of deployment and firewall traversal.

*   **Authentication:** MFA (Multi-Factor Authentication) is mandatory via RADIUS/SAML integration (e.g., Azure AD, Okta).
*   **Encryption:** AES-256-GCM for data encryption; SHA-384 for hashing.
*   **Split Tunneling:** Enabled for latency-sensitive SaaS (Office 365, Zoom), but disabled for critical corporate resource access.

### 4.2 Site-to-Site VPN (Branch-to-HQ)
For connecting satellite offices, utilize **Route-Based IPsec VPNs** (Virtual Tunnel Interfaces).

*   **Protocol:** IKEv2 (more stable, supports MOBIKE).
*   **Encryption:** AES-256; Diffie-Hellman Group 19 or 21 (Elliptic Curve).
*   **Routing:** BGP over IPsec to allow for automatic failover if multiple tunnels exist.

### 4.3 Sample Configuration (Conceptual Logic)
```text
# IKEv2 Proposal
Proposal P1: 
  Encryption: AES-256-GCM
  PRF: SHA-384
  DH Group: 19

# IPsec Policy
Policy Pol1:
  Encryption: AES-256-GCM
  PFS: Group 19

# Tunnel Interface
Interface Tunnel0:
  Source: WAN_IP
  Destination: Branch_WAN_IP
  IP Address: 10.255.0.1/30
```

## 5. Network Monitoring and Observability

### 5.1 SNMP and Polling
Deploy an NMS (Network Management System) like Zabbix or PRTG.
*   **SNMPv3:** Only use v3 for its encryption and authentication. SNMPv2c is prohibited due to plaintext community strings.
*   **Polling Interval:** 5 minutes for standard interfaces; 1 minute for core uplinks.

### 5.2 Flow Telemetry (NetFlow/sFlow)
While SNMP tells you *if* a link is full, NetFlow tells you *why* it is full.
*   **Collection:** Export NetFlow v9 or IPFIX data from the Core Switch to a collector (e.g., Plixer, ELK stack).
*   **Use Case:** Identify "top talkers," detect DDoS patterns, and validate that Guest VLAN traffic isn't leaking into the Server VLAN.

### 5.3 Logging and Alerting
Centralize all logs using a **Syslog** server or SIEM (Splunk, Graylog).
*   **Log Levels:** Set switches to `Informational` (Level 6) and firewalls to `Notice` (Level 5).
*   **Alerting Thresholds:**
    *   **CPU/RAM:** Alert at 80% utilization.
    *   **Interface State:** Immediate alert on `Link Down` for core uplinks.
    *   **VPN:** Alert on repeated failed authentication attempts (Brute force detection).

## 6. High Availability (HA) and Failover

### 6.1 Physical Redundancy
Every access switch must have at least two uplinks to two different distribution/core switches.

### 6.2 Link Aggregation (LACP)
Use **LACP (802.3ad)** to bundle multiple physical links into a single logical Port-Channel. This provides:
*   **Increased Bandwidth:** Aggregate throughput (e.g., $2 \times 10\text{Gbps} = 20\text{Gbps}$).
*   **Deterministic Failover:** If one cable is cut, traffic continues on the remaining link without STP convergence delays.

### 6.3 Spanning Tree Protocol (STP)
To prevent Layer 2 loops, implement **Rapid Per-VLAN Spanning Tree (RPVST+)** or **Multiple Spanning Tree (MST)**.
*   **Root Bridge:** Manually set the Core Switch as the Primary Root and the secondary Core as the Backup Root. Never leave this to default election.
*   **Edge Protection:** Enable `BPDU Guard` and `PortFast` on all end-user ports to prevent unauthorized switches from being plugged in and triggering a topology change.

### 6.4 First-Hop Redundancy Protocol (FHRP)
To ensure the default gateway remains available, implement **HSRP (Hot Standby Router Protocol)** or **VRRP (Virtual Router Redundancy Protocol)**.
*   Two Core switches share a Virtual IP (VIP) (e.g., `10.10.32.1`).
*   If the primary switch fails, the standby assumes the VIP in < 3 seconds, ensuring seamless user connectivity.

## 7. Security Hardening and Best Practices

### 7.1 Device Hardening
The network hardware itself is a target. Apply these settings to all switches and routers:
*   **Disable Unused Services:** Turn off HTTP, Telnet, and CDP/LLDP on untrusted ports.
*   **Management Plane:** Restrict SSH access to the `MGMT_NET` (VLAN 10) only via an ACL.
*   **Passwords:** Use SHA-256 hashing for stored passwords; enforce strong password rotation.

### 7.2 Access Control (Port Security)
Prevent "MAC flooding" and unauthorized device attachment:
*   **Sticky MAC:** Limit each access port to 2 MAC addresses.
*   **802.1X:** Implement Port-Based Authentication using a RADIUS server (e.g., Cisco ISE, FreeRADIUS) to ensure only company-managed devices can access the `USER_CORP` VLAN.

### 7.3 Change Management and Auditing
Network instability is most often caused by human error during changes.
*   **Configuration Backups:** Automate nightly backups of all configs (e.g., using oxidized or Rancid).
*   **Change Window:** All non-emergency changes must be documented in a ticket, peer-reviewed, and executed during a defined maintenance window.
*   **Audit Trail:** Enable `aaa accounting` to log exactly who entered which command on which device.
